# 我实测了 119 个真实 MCP 服务器：55% 根本没法用 —— 我做了一个"质检局"来告诉大家真相

> 项目：https://github.com/hyqzz/trustlens
> 排行榜（119 个服务器，可搜索/筛选/分页，每周自动更新）：https://trustlens.icodestar.net/

## 一、一个让人冒冷汗的现状

MCP（Model Context Protocol）发布不到两年，公共服务器已经超过 **6 万个**。但：

- 跨注册表安全研究显示 **66% 的服务器存在安全问题**
- **88% 的企业 Agent 试点死在上生产之前**——不是模型不行，是没人敢保证工具靠谱
- 你装任何一个 MCP Server 之前，没有任何地方能查到"它到底能不能用、安不安全"

这个生态有应用商店，但没有大众点评；有成千上万的商品，但没有质检局。

## 二、第一批大规模实测：55% 的服务器装完根本用不了

我从 npm / PyPI 注册表选取了 **122 个真实发布的 MCP 服务器**（官方参考实现 + 各来源的社区服务器，全部是真实存在的包），在**隔离环境、无任何 API 凭证**的条件下自动化评测。结果（119 个完成评测）：

| 等级 | 数量 | 占比 | 含义 |
|---|---|---|---|
| A | 9 | 8% | 真正开箱即用 |
| B | 12 | 10% | 可用，但有小问题 |
| C | 25 | 21% | 可用性一般 |
| D | 7 | 6% | 风险偏高 |
| **F** | **66** | **55%** | **装完无法使用** |

**超过一半的公共 MCP 服务器，按文档装完、不配任何额外凭证，根本无法启动或完成协议握手。** 失败原因归类：

- **启动挂起/无响应（55 个）**：进程起来了但 90 秒内不完成初始化握手——很多是静默等待未文档化的配置或交互输入
- **需要 API 凭证才能启动（7 个）**：文档没说，缺了 key 直接崩
- **SDK 兼容性崩溃（3 个）**：官方 Python 服务器因 mcp SDK 改名（`McpError`→`MCPError`）启动即崩

还有 3 个（puppeteer、@enfyra、@mapbox）因会硬挂起评测进程，按方法论暂缓——浏览器自动化等类别需要按工具类型生成合理探针，这本身是下一个方法论课题。

**好消息也有**：`ref-tools-mcp`、`duckduckgo-search`、`ifconfig-mcp` 等拿到了 A 级甚至满分——**"下载量大"和"能用"确实是两回事，"冷门"和"靠谱"也是两回事。**

## 三、TrustLens 是什么

一个开源的 Agent 能力生态信任基准，三样东西：

1. **自动化质检流水线**：隔离环境部署 → 协议握手 → 静态安全扫描（提示注入/数据外发/硬编码凭证）→ 真实试调用 → 多模型兼容性评估 → 0–100 信任分
2. **公开排行榜**：中英双语，**支持搜索、按等级/来源筛选、排序、分页**，每个服务器一页质检报告
3. **CLI**：装任何 MCP 前扫一下

```bash
python -m trustlens check <server-name>
```

**所有评测数据以 JSON 提交在仓库里，git 历史即审计日志**——做信任生意，自己先得透明。

## 四、方法论（透明声明）

- 评测在**剥离环境变量的隔离进程**中执行，被测服务器**不拿到任何密钥**
- **开箱即用基准**：不填任何配置、不配任何 API key，按 `npx -y <pkg>` 标准方式启动，90 秒内完成握手才算"能启动"
- 这个标准是刻意的：**一个需要翻遍文档才知道要配什么才能启动的服务器，对绝大多数用户就是不可用的**
- 评测流水线每周自动复测，结果自动发布
